Slide 2 - Problem and objectives

Thank you, Priyanshu. Walking patterns can change gradually, and it is difficult to understand these changes just by looking at someone. Specialised gait-analysis systems can be expensive and are not always easily available.

A pressure sensor tells us about force-related loading at one position. A motion sensor tells us how the foot moves. We combine both types of information to get a better basic picture.

Our objectives are to collect heel, midfoot and toe readings, read acceleration and angular movement, identify repeated foot-contact events, and display easy-to-understand results through a browser dashboard.

Our project has four parts. First, three FSR sensors at the heel, midfoot and toe measure relative pressure. Second, MPU6050 gives movement data using its accelerometer and gyroscope.

Slide 4 - Sensors, pins and acquisition

Thank you, Shiwani. The main components are the ESP32, three FSRs and an MPU6050. An FSR is a Force Sensitive Resistor, whose resistance changes under force. Each FSR uses a voltage-divider circuit with a 10-kilo-ohm resistor.

We use ESP32 analogue GPIO 34 for heel, GPIO 35 for midfoot and GPIO 32 for toe. These values are raw ADC measurements, not calibrated force in newtons.

The MPU6050 has three acceleration axes and three gyroscope axes. It communicates over I-squared-C with SDA on GPIO 21 and SCL on GPIO 22. The board uses 3.3-volt logic, so we must not connect 5 volts to the GPIO pins.

Slide 5 - Updated live system architecture

Please look at our updated architecture. There are five steps: sensor measurement, ESP32 data acquisition, local serial bridge, browser streaming, and gait-analysis dashboard.

The ESP32 sends ten comma-separated columns: timestamp, heel, midfoot, toe, acceleration X/Y/Z and gyroscope X/Y/Z. The Python bridge opens the correct USB serial port at 115200 baud and validates each numeric row.

The bridge then delivers new packets to the browser using Server-Sent Events. This means the dashboard can update continuously while hardware measurements arrive; no manual CSV import is needed for live mode.

For the present demonstration, the physical ESP32 has already shown real serial output and our earlier recorder saved 1,201 valid rows. The new live bridge has been software-tested using a simulated serial stream; the final end-to-end test on this physical laptop still needs to be confirmed.

Slide 6 - Working methodology and gait phases

The software first reads incoming samples. The FSR sensors can have a non-zero idle reading, so the user can keep the insole stationary and press Calibrate idle baseline. This allows the analysis to subtract resting sensor offsets for gait-event detection, while still displaying the original ADC values.

Next, it observes changes in corrected pressure. A clear foot contact can begin a gait event, and the pressure falling again can mark release. Repeated events allow us to estimate same-foot gait cycle duration.

We estimate cadence from 120 divided by same-foot cycle duration in seconds, assuming alternating steps. We also calculate an approximate stance/swing ratio, pressure transfer and cycle timing variability.

When the pressure signal is weak, the dashboard says insufficient data instead of inventing a walking prediction. This matters because standing or pressing a sensor once is not enough to calculate gait cadence.

Slide 7 - Trained machine learning model

We trained a Random Forest classifier in Python using Scikit-learn. It contains 36 decision trees and uses 440 generated synthetic gait examples, with 330 for training and 110 for a synthetic test split.

The input features include estimated cadence, cycle duration, stance percentage, timing variability, pressure-zone distribution and event flags. The output is steady-like or irregular-like according to the synthetic training patterns.

The trained tree logic was exported to JavaScript, so predictions run inside the browser without a separate model server.

However, synthetic test performance is not evidence of accuracy on actual humans. The current model has not been clinically validated, and it does not detect diseases. Now Shivam will demonstrate the live dashboard and testing.

Remember: If the examiner asks about 100% test accuracy: that number comes only from simple generated synthetic examples; do not claim real-world accuracy.

What is gait?
The manner/pattern in which someone walks.

Why FSR sensors?
They show relative loading at heel, midfoot and toe; not calibrated force.

Why MPU6050?
It supplies accelerometer and gyroscope context for foot motion.

Why ESP32?
It reads FSR ADC channels and MPU6050 I²C measurements, then sends numeric serial rows.

Which serial baud rate?
115200. Firmware outputs time_s,heel,midfoot,toe,ax,ay,az,gx,gy,gz.

How is the dashboard live now?
Python opens USB serial and forwards validated rows over Server-Sent Events to the browser.

Is the live hardware fully verified?
Original serial acquisition is verified, and bridge/UI were separately software-tested; physical end-to-end test of the new combined version remains pending.

What is idle calibration?
It estimates baseline ADC values while the insole is stationary, so changes can indicate pressure contact.

What is cadence?
Estimated steps per minute from same-foot gait cycles; with one insole we assume alternating steps.

Why does it show insufficient data?
Too few valid contact cycles or inadequate FSR variation; reporting a number would be misleading.

Which ML model?
Synthetic-trained 36-tree Random Forest with 10 gait features.

How many training samples?
440 generated synthetic examples, including a 110-sample synthetic holdout split.

What if ML gives a very high score?
It is a synthetic-pattern class score, not disease probability or clinical accuracy.

Can it detect Parkinson’s?
No. No disease-labelled real training or medical validation exists.

How do you save data?
Export live sensor CSV; session metrics also save locally in the browser.

Can it calculate left vs right balance?
No, a single three-zone insole cannot measure both feet accurately.

What if the live port is busy?
Close Arduino Serial Monitor and any Python recorder holding the same USB port.
